# Agent Note: 私有 AI Infra 贡献雷达

Status: implemented

## Problem

现有 issue scout 只看四仓的入门标签与标题，把零评论等同无人认领；实际开放的
零评论 issue 也可能已有修复 PR。个人需要跨仓的持续发现、可追溯核查和参与跟进，
避免只收藏链接或重复提交别人已经在做的修复。

## Decision

在独立私有仓维护 JSON 配置、Python 标准库扫描器和 GitHub Actions 每日任务。
使用 gh 的只读 GraphQL 调用，采集近期开放 issue、入门标签、主线标题主题与 Discussion，
对每仓高分候选和人工固定条目分页核查评论与交叉引用。按技能相关性与参与阻力
排序，分别展示调查、协作验证、讨论和需核查的候选；分数不是解决成功率。

个人 triage 和参与台账是人工源；生成器只写 data/ 与 reports/。扫描失败保留上次
成功报告并返回非零。每日保存压缩历史，最新数据保留来源、截断与覆盖边界。
所有公开反馈均通过用户审阅；定时任务只提交本私有仓生成文件。

## Alternatives considered

- 扩展现有 Bash scout：迁移成本最低，但评论分页、Discussion 和跨引用需要结构化
  状态，继续使用多层 shell 管道难以准确表达核查边界。
- 对全量 issue 和全部评论做每日扫描：覆盖最强，但大型仓的历史数据与 API 预算
  不符合个人每日阅读量；采用显式抽样，并持续追踪固定条目。
- 接入付费模型自动判定并公开评论：可生成更丰富的摘要，但当前没有配置模型服务，
  也没有授权自动发言；保留透明规则和人工分析，后续按实际需求重访。

## Verification

- 初始化时十二仓真实扫描采集 518 个条目，核查 81 个重点线程，生成 25 项机会清单；
  当前快照是每日窗口，不是全量问题的技术审查。
- 16 项离线测试覆盖评论后页的认领、释放、关闭关联与普通跨引用、分页与文本截断、
  人工判断的状态约束、RFC 分类、主题去重、失败保留旧报告、人工文件不被覆盖。
- `npm run verify-notes` 校验笔记树、格式与归档封印。GitHub 部署验证通过
  `.github/workflows/ci.yml` 与 `daily-scan.yml` 的实际运行记录追溯。

## Consequences

- 收益：个人参与从标题收藏变成有来源、参与方式、资源边界和后续动作的持续工作台。
  人工记录与生成物分离，扫描不更改自己的贡献进度，也不自动发公开消息。
- 代价：规则无法替代技术评审；认领、跨引用语义及原帖硬件可能有歧义，报告明确
  不确定性。原帖正文与评论摘录会截断；PR 逐行评审需要本人阅读。
- 上限：每日窗口不是全量覆盖，分页有预算。日期快照同日重跑覆盖当日文件，细节
  通过 Git 历史追溯；大仓样本或历史体积超出日常阅读量时，重访检索词与存储策略。
